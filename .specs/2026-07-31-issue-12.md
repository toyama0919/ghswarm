# Make the GitHub Issue the single source of the spec (drop committed `.specs/*.md`)

## Background / Purpose

Today an approved spec is committed to the work branch as `.specs/YYYY-MM-DD-issue-N.md` and merged into `main` along with the implementation PR. As a result the **point-in-time information** a spec carries (line-number references, old names, the architecture assumptions of the day, task checklists) is permanently persisted into `main`, where it becomes drifted noise for both AI and humans reading the repository.

Meanwhile the spec's prose is already duplicated almost verbatim in the Issue body, and ghswarm already fetches the Issue body at runtime for state management (the `GHSWARM_STATE` block lives inside the Issue body). What the spec file actually provides at runtime is only these two things:

1. the frontmatter `verify:` (run via `orchestrator._verify_steps_for` → `spec.verify_steps`)
2. the body prose (`orchestrator._spec_block` embeds `spec.body[:4000]` into the implement/review prompts)

Of these, (2) is already duplicated in the Issue body — the implement prompt separately passes `Issue body:\n{stripped[:2000]}` ([orchestrator.py:278](../src/ghswarm/orchestrator.py#L278)). And (1) can be moved into a separate block of the Issue body. So we can **make the Issue the single source of the spec and stop committing `.specs/*.md` entirely**.

Adding a note to `AGENTS.md` saying "`.specs/` is not the current specification" is not adopted: ghswarm drives many repositories, so it would have to be written per repository, which is impractical.

## Requirements

- Do not commit `.specs/*.md` to the work branch or to `main`. Make the Issue the single source of the spec.
- Put the verify configuration in a dedicated comment block **`GHSWARM_VERIFY`** in the Issue body. Keep it separate from `GHSWARM_STATE` (which the machine replaces every iteration) so verify survives every state rewrite.
  - The verify schema itself (legacy = string / list of strings; new form = list of `{path, command}`) is **unchanged**. The `verify_steps` normalization logic in `spec.py` is reused as-is. Only its storage location moves, from "file frontmatter" to "the Issue's `GHSWARM_VERIFY` block."
- **Do not change any existing body-rewriting path.** In particular the behavior and span assumptions of `strip_state` / `parse_tasks` / `check_task` must stay untouched (see Design approach 1).
- The spec context handed to the implement/review agents comes from the **Issue body prose** (both the `GHSWARM_STATE` and `GHSWARM_VERIFY` blocks stripped), not from a spec file in the worktree.
- Change the start gate (the safety valve that refuses to start on an unprepared Issue) from "a spec file exists in the worktree" to "**a `GHSWARM_VERIFY` block exists in the Issue body**" (= spec metadata present).
  - The **presence** of the `GHSWARM_VERIFY` block is the criterion; an empty verify inside it (local verification skipped) still counts as "spec'd." "No block" = "not spec'd yet."
  - Put the gate in both `_implement` and `_review` (the Issue body is already in hand, so the check is cheap; this also closes the existing hole where an Issue resumed at `next_action: ai_review` passes no gate at all).
- **A broken verify must not take the loop down with an exception.** If the verify block's YAML is malformed, or `verify_steps` normalization raises `ConfigError`, **block that Issue as `verify_invalid`** (do not raise an exception that takes other Issues with it). Do not treat "empty verify (skip verification)" and "broken verify" as the same thing.
- ghswarm creates the branch and the PR. ghswarm-spec (Line 1) cuts no branch, commits no spec file, and opens no spec PR.
- **Push the branch to origin when implement succeeds.** Since Line 1 no longer pushes, without this a lost worktree takes the WIP with it (today `ensure_worktree` can restore from origin). This preserves the existing "WIP is left on the branch" guarantee.
- Keep the Issue ↔ PR cross-links. Put `Refs #N` in the PR body (never `Closes`, which would bypass ghswarm's merge gate, per existing convention), so both directions are traceable via GitHub's automatic cross-reference plus the Issue's state (`pr_url` / `pr_number`).
- Do not break existing runtime behavior (verify step order and fail-fast, start-gate safety, cross-links, WIP preservation).

### Acceptance criteria

- For an Issue that has only a `GHSWARM_VERIFY` block in its body and no spec file, implement/review resolve both the spec context and verify from the Issue and work.
- An Issue with no `GHSWARM_VERIFY` block is blocked at the start gate (`spec_missing`) — via both the `_implement` and the `_review` path.
- An Issue whose `GHSWARM_VERIFY` YAML is malformed is blocked as `verify_invalid`, and no exception propagates out of the loop.
- Applying `_persist` (= `write_state(strip_state(body), state)`) repeatedly preserves the `GHSWARM_VERIFY` block, the prose, and the checklist.
- `check_task` / `check_tasks` write the checkbox at the correct position regardless of whether a `GHSWARM_VERIFY` block is present or where it sits in the body.
- Starting with no pre-existing branch or PR, implement → `_create_pr` creates a new PR whose body contains `Refs #N`.
- After a successful implement, the branch exists on origin.

## Design approach

### 1. The `GHSWARM_VERIFY` block, and leaving existing paths intact

Add a `GHSWARM_STATE`-shaped HTML comment block holding YAML (invisible when rendered):

```
<!-- GHSWARM_VERIFY_START
verify:
  - uv run --extra dev ruff check .
  - uv run --extra dev python -m pytest -q
GHSWARM_VERIFY_END -->
```

Add `GHSWARM_VERIFY_START` / `GHSWARM_VERIFY_END` constants, a regex, and these helpers to `state.py`:

- `parse_verify_meta(body) -> dict`: `yaml.safe_load` the block's contents and return the `{"verify": ...}` dict; `{}` if there is no block. **A `yaml.YAMLError` must not be swallowed into `{}`** — since malformed verify has to become a block (see below), collapsing it to `{}` (= empty verify = skip) is wrong. For example raise `ConfigError` for the caller to catch, or return `(ok, meta)`. This is deliberately different from the existing `parse_spec`, which does swallow YAMLError ([spec.py:107-112](../src/ghswarm/spec.py#L107)).
- `has_verify_meta(body) -> bool`: whether the block exists (for the start gate). Its contents do not matter.
- `strip_verify(body) -> str`: remove the block.
- `prose(body) -> str`: prose extraction for prompts = `strip_verify(strip_state(body))`.

**Important — do not change existing paths.** `strip_state` and `parse_tasks` are **not modified at all**, because:

- Persistence really runs through `write_state(strip_state(fresh.body), state)` ([orchestrator.py:1083](../src/ghswarm/orchestrator.py#L1083) in `_persist`, plus [:345,:354](../src/ghswarm/orchestrator.py#L345)). If `strip_state` also removed verify, **the very first `_persist` would delete `GHSWARM_VERIFY` from the body**, and the next iteration would block with `spec_missing` (self-destruction).
- `parse_tasks` returns **absolute offsets** into a `strip_state`-ed string ([state.py:102-118](../src/ghswarm/state.py#L102)), and `check_task` writes `[x]` back into a separately built copy of that same string using those spans ([state.py:144-150](../src/ghswarm/state.py#L144), [orchestrator.py:346](../src/ghswarm/orchestrator.py#L346)). Stripping verify on only the parse side desynchronizes the two strings, so `[x]` lands in the wrong place and corrupts the Issue body.
- The worry that "verify command lines would be picked up as checkboxes" **does not hold**: `_TASK_RE` ([state.py:23](../src/ghswarm/state.py#L23)) matches only `- [ ]` / `- [x]`, never `- uv run ...`. The only reason to strip verify is to keep the YAML out of the prompt, so stripping is confined to `prose()`, i.e. prompt generation.

As a result the block's position in the body has no bearing on span correctness (no position-dependent implicit invariant is created). The recommended order when ghswarm-spec files an Issue is "prose + task checklist → `GHSWARM_VERIFY` → `GHSWARM_STATE`" (`write_state` always appends state last), but that is for readability, not correctness.

**Constraints**: because the block lives in an HTML comment, verify command strings cannot contain `-->` or `GHSWARM_VERIFY_END`. Document this in the README and the skills. Humans also cannot read verify in the GitHub UI, so document reading it with `gh issue view <N> --json body -q .body`.

### 2. Point orchestrator's spec references at the Issue body

- `_spec_block` is built from the Issue body prose: `prose(issue.body)[:4000]`. Drop the `spec_path` dependency from the header and use `--- spec (issue #N) ---`. All 5 call sites (implement [:271](../src/ghswarm/orchestrator.py#L271), review [:385](../src/ghswarm/orchestrator.py#L385), address_review [:586](../src/ghswarm/orchestrator.py#L586), conflict [:667](../src/ghswarm/orchestrator.py#L667), ci-fix [:786](../src/ghswarm/orchestrator.py#L786)) have `issue` in scope, so the body can be passed.
- `_verify_steps_for` resolves from `parse_verify_meta(issue.body)` via `Spec(meta=...).verify_steps` instead of `_load_spec` (file read). Resolution into `ResolvedStep` (sandbox assignment through `cfg.verify.sandbox_for`) is unchanged.
- **Signature change caution**: `_spec_block` / `_verify_steps_for` currently take `(state, worktree)`, and several tests monkeypatch them as `lambda state, worktree: ...`. Switching to a body parameter breaks all of those at once (see task breakdown).
- Verify-resolution failure (malformed YAML in `parse_verify_meta`, or `ConfigError` from `verify_steps`) is caught in each phase and turned into a `verify_invalid` block (Issue comment + `_enter_blocked`, mirroring `_block_for_missing_spec`). `Orchestrator.process` only catches `GitError` ([orchestrator.py:116](../src/ghswarm/orchestrator.py#L116)), so left alone the exception escapes to `cli.py`'s `except Exception` ([cli.py:404](../src/ghswarm/cli.py#L404)) and aborts the entire cycle for that repository, leaving the already-acquired busy label in place until lock_ttl.
- Delete `_load_spec`. From `spec.py`, **delete `parse_spec` and `Spec.body`**, keeping only `Spec` (`meta` + `verify_steps`) and `VerifyStep`. Rewrite the module docstring around "verify normalization from Issue metadata."

### 3. Start gate

- Replace `_spec_path_set` at the top of implement ([:225](../src/ghswarm/orchestrator.py#L225)) with `has_verify_meta(issue.body)`, and put the same gate in `_review` (the `check_spec` argument becomes unnecessary and is removed; its only `True` caller is [:237](../src/ghswarm/orchestrator.py#L237)).
- Remove the `_spec_file_in_worktree` checks ([:260](../src/ghswarm/orchestrator.py#L260), [:379](../src/ghswarm/orchestrator.py#L379)). The gate can now be evaluated from the Issue body alone, before the worktree is created.
- Collapse `_block_for_missing_spec`'s reason to `spec_missing`, removing `spec_not_in_branch` and its comment wording. Add the new `verify_invalid` block path.
- Delete the now-unused `_spec_present` / `_spec_file_in_worktree` / `_spec_path_set` / `_load_spec`.

### 4. Drop `spec_path` from state

Remove `IssueState.spec_path`. `from_dict` ignores unknown keys ([state.py:65](../src/ghswarm/state.py#L65)), so a leftover `spec_path` in existing Issues' JSON is safely ignored. Also remove the places that referenced it (the `_block_for_missing_spec` wording, etc.).

### 5. Branch/PR creation and WIP preservation

- Creating the branch and PR needs no new code. `_ensure_worktree_git` → `git.ensure_worktree(branch, base_branch, path)` creates the branch from `origin/<base>` when it does not exist on origin ([git_ops.py:140-148](../src/ghswarm/git_ops.py#L140)). `_create_pr` (starting at [orchestrator.py:430](../src/ghswarm/orchestrator.py#L430); the reuse/create split is at [:441-464](../src/ghswarm/orchestrator.py#L441)) creates a PR with `Refs #N` itself when `pr_for_branch` finds nothing.
- **One addition is required, though**: since Line 1 no longer runs `git push -u origin issue-N`, there is a window where origin has no branch until `_create_pr`. If the worktree is lost during that window, `ensure_worktree`'s origin-restore path ([git_ops.py:128-138](../src/ghswarm/git_ops.py#L128)) is unavailable, so it recreates from base and silently loses the WIP. The implement-failure comment "partial changes are left on branch ..." ([orchestrator.py:325](../src/ghswarm/orchestrator.py#L325)) would also point at a local branch invisible to humans. **Push the branch after the implement savepoint** to keep the existing guarantee.
- The longer window in which no PR exists (progress not visible on GitHub) is accepted. The Issue ↔ PR cross-link is established at `_create_pr`.

### 6. Bootstrapping this Issue (self-modification)

This spec changes ghswarm's own state model, and **ghswarm implements it autonomously by reading its own Issue**. The ghswarm that runs is `.venv/bin/ghswarm` → the repository's `src/ghswarm` (i.e. **the old code on the main checkout**), not the new code in the worktree. Therefore:

- **This Issue is filed in both the old and the new form**: (a) as before, a `.specs/YYYY-MM-DD-issue-N.md` committed to the branch with `spec_path` written into state (to satisfy the old code's start gate and verify resolution), and (b) a `GHSWARM_VERIFY` block in the Issue body (for the new code to read). State in the spec / Issue that this is an exception for this migration PR only.
- The implementation must not break the old code's assumptions mid-loop. **Deleting `.specs/` is not done in this Issue** (see out of scope). The moment it is deleted, the old gate blocks with `spec_not_in_branch` and the remaining tasks stop. Worse, `_load_spec` returns an empty `Spec` with only a warning when the file is missing ([orchestrator.py:1055-1062](../src/ghswarm/orchestrator.py#L1055)), so the gate-less `_review` / `_address_review` / `_fix_ci` / `_resolve_conflict` paths would proceed as "successful" **with an empty verify, i.e. unverified** — a silent failure.
- There are currently 0 open Issues, so this Issue is the only migration target. **No compatibility fallback code is added** (no backward compatibility by policy). For other users, document the migration procedure ("append a `GHSWARM_VERIFY` block to each open Issue before upgrading") in the README and the `ghswarm-check` skill.

### 7. Removing `spec_dir`

- Delete the `RepoConfig.spec_dir` field ([config.py:142](../src/ghswarm/config.py#L142)) and its parse ([config.py:673](../src/ghswarm/config.py#L673)). Remove it from `config.example.yaml` (line 38) as well. There are no other runtime consumers, so removal is safe.
- No backward compatibility, but no silent ignoring either. Following the existing `test_command`/`sandbox` → `verify` migration `ConfigError` pattern ([config.py:524-525](../src/ghswarm/config.py#L524)), **raise a migration `ConfigError` when a leftover `spec_dir` key is detected**. Since `spec_dir` can be written under both `defaults` and `repositories.<alias>`, **detect it in both**.
- Remove `spec_dir` from the `ghswarm config` JSON output ([cli.py:164](../src/ghswarm/cli.py#L164)).
