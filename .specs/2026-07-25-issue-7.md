# Support per-directory verify for monorepos

## Background / Purpose

Today, `RepoConfig` (`src/ghswarm/config.py`) can only express verify (setup/test verification) as two single values:

- `test_command: str` — one verification command for the whole repository.
- `sandbox: SandboxConfig` — one execution environment for the whole repository (`driver: none` = local, or `driver: docker` + `image`).

The spec-side frontmatter `verify` (`.specs/*.md`, `src/ghswarm/spec.py`) mirrors this limitation: it only supports a single command (a string, or a list joined with `&&`), and always runs it under config's `sandbox`. Precedence today is "spec's `verify` > config's `test_command`" (`orchestrator.py`'s `_test_command_for`).

This doesn't support monorepos (e.g. a `terraform/` directory alongside a `backend/` directory in the same repository) where:

- verify commands differ by directory (`terraform validate` vs `pytest`),
- the required execution environment differs by directory (`terraform` runs locally, `backend` needs a specific Docker image),
- a single Issue/PR touches multiple directories at once and both verifications must run in sequence.

This spec resolves that: execution environments are declared per directory, and the actual verification steps to run are assembled per Issue on the spec side.

## Requirements

### 1. Config side: drop `test_command` / `sandbox`, consolidate into `verify:`

Remove the `test_command` and `sandbox` fields from `RepoConfig` and replace them with a new `verify` field (a newly defined type, referred to below as `VerifyConfig`). **No backward compatibility with the old `test_command` / `sandbox` keys is required.** If a config file still has these old keys, raise a `ConfigError` prompting migration to `verify:` (do not silently ignore them).

Config's `verify:` accepts two shapes:

- **Single form** (the default for most non-monorepo repositories): a mapping with only `sandbox`, no `command`.

  ```yaml
  verify:
    sandbox:
      driver: none   # also the default when omitted
  ```

  In this case, this `sandbox` is used for the whole repository, for every step regardless of `path`.

- **List form** (a monorepo "path → sandbox" registry): a list of mappings, each with `path` and `sandbox`. No `command` here — the command is decided on the spec side.

  ```yaml
  verify:
    - path: terraform
      sandbox:
        driver: none
    - path: backend
      sandbox:
        driver: docker
        image: python:3.12
  ```

If `verify:` is unset, treat it as "empty registry," which falls back to `driver: none` as described below.

**Config's `verify` never carries a `command`**, in either shape. As a direct consequence, an Issue whose spec frontmatter has no `verify` loses one of the two fallback layers that existed before ("spec's verify → config's test_command → skip") — local verification is now **always skipped** in that case (there is no repo-wide default verification command left to fall back to on the config side). This is an intentional behavior change: the ghswarm-spec skill always generates a per-Issue `verify` frontmatter, so in normal operation this gap should not matter.

### 2. Spec side: frontmatter `verify:` carries the actual steps to run

Extend `Spec`/`parse_spec` in `src/ghswarm/spec.py` to accept two shapes for frontmatter `verify:`:

- **Legacy form** (kept as-is): a string, or a list of strings joined with `&&` into a single command (same behavior as today's `verify_command`). Since it has no `path`, its execution environment is "config's `sandbox` if config's `verify` is in single form, else `driver: none`" (the list-form registry is keyed by `path`, so a path-less legacy step can't look anything up in it).
- **New form**: a list of mappings, each with both `path` and `command`. **Both are required** (the AI is expected to generate these per task; omission is not allowed). `sandbox` is not written on the spec side — each entry's execution environment is resolved by matching its `path` against config's `verify` (when in list form).

  ```yaml
  ---
  verify:
    - path: terraform
      command: "terraform validate"
    - path: backend
      command: "pytest"
  ---
  ```

`path` matching is exact string comparison. If config's `verify` is in single form, that `sandbox` is used regardless of `path`. **If config's `verify` is in list form and no entry matches, fall back to `driver: none`** (do not error).

**The legacy form and the new form must not be mixed within the same spec's `verify:`** (distinguish by YAML type: a string or list of strings is the legacy form; a list of mappings is the new form. A list mixing mappings and strings is a `ConfigError`-equivalent error).

`path` validation follows the same rules as config's `path` (registry keys): no absolute paths, no `..` escaping the worktree, no empty string. Raise a clear error on violation (existence of the directory itself is not checked — if it doesn't exist, the command will simply fail at execution time).

### 3. Execution semantics

A single verify target (the spec's `verify`) consists of multiple "steps" (one step for the legacy form, one per entry for the new form). At execution time:

- Run all defined steps, in order, every time. **No git-diff-based filtering of which steps run** (always attempt every defined step).
- **Stop at the first failing step** (once a step's exit code is non-zero, do not run the remaining steps).
- If there are zero steps (the spec has no `verify`, or an empty list), follow the existing "an empty verify command skips verification and is treated as success" behavior (`run_tests`'s existing early return) — treat it as **success** and do not enter the self-healing retry loop.
- Concatenate each step's output with a header identifying its `path` (a legacy, path-less step uses a fixed marker such as `"(root)"`). On failure, pass the combined log up to (and including) the failing step — not the steps after it — into the self-healing loop's re-prompt to the implementation agent.
- Each step's execution cwd is `<worktree>/<path>` if `path` is set, else the worktree root. Under Docker, the whole worktree is still mounted exactly as today; only the container's working directory is set to that step's `path` (no need to mount just the subdirectory). See the sandbox.py change in "Design approach" for details.
- **Timeout is per step**, using today's `run_tests` default (1800s) per step (the more steps, the more the total ceiling grows proportionally; there is no cross-step aggregate timeout).
- **`is_transient` is evaluated against the combined log up to the point of stopping**, using the existing logic (not per-step output, but the concatenated output leading up to the failure).

### 4. Affected call sites

The following 3 call sites in `src/ghswarm/executor.py`, which use verify (formerly `test_command` + `sandbox`), need to switch to the new multi-step execution:

- `execute_with_self_healing` (verification after an implementation agent run; drives the self-healing loop on failure)
- `resolve_conflict_with_agent` (verification after conflict resolution)
- the CI-failure auto-fix flow (verification after handing CI failure logs to the implementation agent for a fix)

All three receive a single `test_command: str` via `orchestrator.py`'s `_test_command_for`, so the equivalent resolution logic needs to be replaced with "build the list of steps to run from the spec's `verify` frontmatter + config's `verify` (registry)."

**A 4th call site: `orchestrator.py`'s `_run_worktree_setup`** (runs the `worktree_setup` command exactly once, right after a worktree is newly created) also uses `make_runner(self.cfg.sandbox)`, and is affected by dropping `cfg.sandbox`. `worktree_setup` isn't tied to any particular `path` (it sets up the whole worktree), so resolve it via `sandbox_for(path=None)`. This requires no new rule: if config is in single form, that `sandbox` is used; if in list form, `path=None` naturally matches no entry, so the existing fallback (`driver: none`) applies as-is.

## Out of scope

- Filtering which steps run based on git diff (an optimization that only runs steps relevant to the changed files — not done here).
- Parallel execution of multiple steps (always sequential, stop at the first failure).
- Backward compatibility for `test_command` / the old `sandbox` (this migration is treated as a breaking change, surfaced explicitly via `ConfigError`).
- Partial/glob matching on `path` (exact match only).
- Per-step `sandbox` overrides on the spec side (always resolved from config's registry by `path`).
- Retry-unit optimization in the self-healing loop (rather than re-running only the failed step, a retry always re-runs every step from step 1 — following the existing "redo the whole attempt" structure of `execute_with_self_healing`).

## Design approach

- **Reuse `SandboxConfig` as-is** (the shape of `driver` / `image` / `network` / `user` / `env` / `env_passthrough` / `volumes` / `isolate_dirs` does not change). What changes is only "how many of them hang where."
- **Config side**: add `verify: VerifyConfig` to `RepoConfig` (remove the `test_command` and `sandbox` fields). Define `VerifyConfig` as a new dataclass able to represent either "single form" (just a `default_sandbox: SandboxConfig`) or "list form" (a `path -> SandboxConfig` sequence of entries) — e.g. normalizing the single form into a one-entry `entries: list[tuple[str | None, SandboxConfig]]` with `path=None` is a fine internal representation; pick whatever shape is convenient at implementation time. Give it a resolver method like `sandbox_for(path: str | None) -> SandboxConfig` so callers (executor/orchestrator) don't need to duplicate the resolution logic.
  - Replace `_load_sandbox` and the surrounding load logic (in `config.py`) with a new load function that reads the `verify:` block, distinguishes single vs. list form, and builds a `VerifyConfig`.
  - If a config file still has `test_command` or `sandbox` keys (directly under the top-level repo block), raise a `ConfigError` with a message prompting migration.
- **Spec side**: replace `Spec.verify_command` (a property returning a single string) in `src/ghswarm/spec.py` with something that can express multiple steps (e.g. `Spec.verify_steps -> list[VerifyStep]`, where `VerifyStep` holds `path: str | None` and `command: str`). Normalize the legacy form (string / list of strings) into a single `path=None` step. For the new form (a list of mappings with `path` + `command`), turn each element directly into a `VerifyStep`. Raise a `ConfigError` (or an equivalently clear exception) if any entry is missing `path` or `command`.
- **Execution side**: add a helper to `executor.py` (e.g. `run_verify_steps`) that runs a resolved list of steps (`command` + execution cwd + `ShellRunner`) in order, stopping at the first failure and aggregating the result; use it in place of `run_tests` at the 3 call sites. Step resolution (matching the spec's `verify_steps` against config's `VerifyConfig.sandbox_for` to decide execution cwd/runner) happens where `orchestrator.py`'s `_test_command_for` used to (feel free to rename the method); `executor.py` then just receives "a list of already-resolved steps" (this keeps the existing division of labor: orchestrator assembles, executor executes).
- **`config.example.yaml`**: remove the `test_command:` and top-level `sandbox:` examples, replace with commented examples for both the single-form and list-form `verify:`.
- **`src/ghswarm/sandbox.py` (`DockerRunner`)**: currently, [`_build_run_command`](src/ghswarm/sandbox.py#L120) uses the same `cwd` passed in for both the volume mount (`-v {cwd_abs}:/workspace`) and the container's working directory (`-w /workspace`). Now that a step's `path` is a subdirectory inside the worktree, **passing `cwd=<worktree>/<path>` as-is would mount only that subdirectory**, which violates the requirement in section 3 that the whole worktree stay mounted while only the working directory changes. Change `ShellRunner.run`'s signature (or how `DockerRunner` is invoked) to separately accept "the root to mount (always the whole worktree)" and "the container's working directory (the `path`, relative to `/workspace`)". `LocalRunner` can keep using `cwd` as-is (local execution has no concept of a mount). `isolate_dirs` (tmpfs mounts relative to `/workspace`) and `_resolve_git_common_dir` are unaffected — both stay relative to the mount root.
- **Documentation**: replace the `test_command` / `sandbox` entries in `README.md`'s config reference table and the `### sandbox` section with `verify:` documentation. Update the frontmatter `verify` description in `src/ghswarm/skills/ghswarm-spec/SKILL.md` (statements like "a string or a list" and "falls back to config's `test_command`") to match the new form and the updated fallback rules — this skill governs the frontmatter format of specs it generates going forward, so leaving it stale would keep producing specs in the old shape.
