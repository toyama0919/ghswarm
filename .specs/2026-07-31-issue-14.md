# Place the state metadata block at the top of the Issue body

## Background / Purpose
ghswarm embeds its state metadata as an HTML comment (`<!-- GHSWARM_STATE_START ... GHSWARM_STATE_END -->`) at the **end** of the Issue body ([state.py](../src/ghswarm/state.py)).

When inspecting the state via Edit / raw view, a long body (background, requirements, task checklist) forces scrolling to the bottom to reach it, which is inconvenient. Placing the state block at the **top** of the body lets it be checked immediately right after the Issue is opened for editing.

## Requirements
- `write_state` outputs the state block **before** the human-readable body.
- `strip_state` / `parse_state` / `parse_tasks` produce results identical to today (stay position-independent; no regression).
  - In particular `strip_state(write_state(human, state)) == human` must hold (reliably remove the leading newline left by a top-placed block).
- Existing Issues (state at the end) migrate naturally to the top on the next `write_state`. No data migration is performed.

## Design approach
- Change only two functions in [state.py](../src/ghswarm/state.py):
  - `write_state` ([state.py:79-83](../src/ghswarm/state.py#L79-L83)): against the body with any existing block removed, concatenate the block at the **front instead of the end**. When the body is empty, return `<block>\n` (block + one trailing newline).
  - `strip_state` ([state.py:86-88](../src/ghswarm/state.py#L86-L88)): currently only `rstrip()`. When a block sits at the top, a **leading newline remains** after removal, so change to `strip()` to remove leading and trailing whitespace together. This preserves `strip_state(body) == human` ([test_state.py:35](../tests/test_state.py#L35)).
- Position detection is done with the `_STATE_RE` regex ([state.py:17-20](../src/ghswarm/state.py#L17-L20)) and is position-independent, so no change is needed on the `parse_state` / `parse_tasks` side. Reading existing Issues (state at the end) keeps working as before.
- The output format (one blank line between the block and body, a single trailing newline) follows the current appearance.
- Update the stale documentation accordingly (the "at the end of the body"-style descriptions): the module docstring at [state.py:3](../src/ghswarm/state.py#L3), the `write_state` docstring ([state.py:80](../src/ghswarm/state.py#L80), "appended"), and the relevant line in [README.md](../README.md).
- Note (no practical impact): the span returned by `parse_tasks` is an offset relative to the stripped body. Because the state currently sits at the end, this offset happened to also match the full (unstripped) body; with a top-placed block that coincidence no longer holds. All current callers apply the span against the stripped body, so there is no practical impact.

### Out of scope
- Rendering the state visibly in the GitHub UI. It stays an HTML comment, so even at the top it remains hidden in the github.com rendered view (visible only via Edit / raw). Turning it into visible text is not done here.
- Removing the `busy_owner` field. It is in use by fast stale-lock reclaim ([labels.py:82-84](../src/ghswarm/labels.py#L82-L84)) and the blocked notification ([orchestrator.py](../src/ghswarm/orchestrator.py)), so it is kept as-is.
- Changing the state schema or adding/removing fields.
